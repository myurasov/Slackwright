--------------------------------------------------------------------------------
1. PROBLEM AND SOLUTION
--------------------------------------------------------------------------------

PROBLEM
  Official Slack bot apps (and most "Slack MCP" integrations) are limited
  by the bot scopes the workspace admin grants them. In practice that
  means:
    * the bot only sees DMs / MPIMs / channels it is explicitly added to,
    * externally-shared channels are usually excluded by org policy,
    * per-tenant exclusion lists at the API gateway block whole channels,
    * the result-set cap is tighter than what the web client allows.

  As a result, "fetch every message I sent in the last 30 days" is
  impossible through normal bot integrations for most users.

SOLUTION
  slackwright drives a real, headed Chromium window through Playwright,
  lets the user log in to slack.com normally (SSO, MFA, hardware keys —
  whatever their org requires), and then uses the resulting authenticated
  browser context to call Slack's internal web-search endpoint
  `<workspace>/api/search.modules.messages`. That is the same endpoint
  the desktop client uses; anything you can read in slack.com is reachable
  here, with no bot scopes involved.


--------------------------------------------------------------------------------
2. SCOPE
--------------------------------------------------------------------------------

IN SCOPE
  * Read-only message extraction from Slack workspaces the user can
    already log into.
  * Search-style queries (from / to / with / in / before / after / on /
    during, plus arbitrary keyword text).
  * Resolution of Slack IDs to human names + emails, channel names, etc.
  * Optional download of message attachments.
  * Output in a sharded per-message JSON tree + YAML caches that
    downstream tools can consume without conversion.

OUT OF SCOPE
  * Posting messages, editing messages, reactions, status updates, any
    kind of write to Slack.
  * Bypassing two-factor auth, captchas, or any auth challenge.
  * Fetching content from workspaces the user is not a member of.
  * Real-time streaming / event subscriptions (this is a search-style
    extractor, not a bot).
  * Re-implementing the Slack desktop client.


--------------------------------------------------------------------------------
3. ARCHITECTURE
--------------------------------------------------------------------------------

slackwright is a small Python package (src layout) plus a CLI. The
modules are intentionally thin and orthogonal so they can be unit-
tested in isolation.

  src/slackwright/
    __init__.py     public surface + version
    __main__.py     enables `python -m slackwright`
    paths.py        state-dir resolution (~/.cache/slackwright/ default)
    auth.py         headed Playwright login + token / cookie extraction
    client.py       Slack web-API client (over Playwright page.request)
    resolver.py     id / email / handle / name -> Slack entity resolution
    search.py       SearchPlan + paginated runner + month chunker
    files.py        attachment downloader
    archive.py      sharded JSON tree + YAML caches + matches.jsonl
    progress.py     stderr progress display
    cli.py          argparse entry-point dispatching to the modules above

  tests/            pytest suite — see section 11

DEPENDENCIES
  * playwright >= 1.41, < 2.0   (drives the browser + HTTP)
  * PyYAML >= 6.0               (writes _users / _channels caches)
  * Python >= 3.10

  Dev only: pytest, pytest-asyncio, ruff. No other runtime deps. The
  package must remain installable on plain pip on macOS / Linux /
  Windows without compilation steps.

DATA FLOW
  1. `slackwright login` opens headed Chromium pointed at the workspace.
     The user signs in. Once `window.boot_data.api_token` shows up we
     extract it + the cookie jar and persist Playwright storage state.
  2. `slackwright fetch ...` opens a headed-or-headless Chromium with
     that storage state, navigates to the workspace (so cookies have
     the right origin), and uses page.request.post() to call Slack's
     web API endpoints.
  3. EntityResolver translates --from / --to / --with / --in args into
     Slack IDs and handles. First missing-name lookup triggers a one-
     time users.list / conversations.list pull (cached on disk).
  4. SearchRunner builds the query string (`from:@handle in:#channel
     after:YYYY-MM-DD ...`), paginates through all results, and slices
     date ranges by month so each chunk stays under Slack's 100 x 100
     result cap. Cross-chunk dedup on (channel_id, ts).
  5. ArchiveWriter writes each match to disk in the canonical layout
     (section 4), incrementally appending to matches.jsonl as it goes.
  6. If --with-files is set, FileDownloader walks every match's `files`
     array and downloads each attachment via the same authed context.
  7. Resolver fills in any user / channel IDs we encountered but had
     not previously cached, then writes _users/ + _channels/ YAMLs.
  8. ArchiveWriter writes _index.yaml summarising counts + the search
     plan + truncation warnings.


--------------------------------------------------------------------------------
4. OUTPUT LAYOUT
--------------------------------------------------------------------------------

DEFAULT FORMAT (--format archive, the only format that produces the
full sharded tree):

  <out>/
    messages/YYYY/MM/DD/YYYY-MM-DD-<chan-slug>-<hash8>.json
    _users/<U_id>.yaml
    _channels/<C_id>.yaml
    _files/<F_id>/<safe_filename>      # only when --with-files
    _files/<F_id>/_meta.json
    _index.yaml
    matches.jsonl

  <hash8> = first 8 hex chars of sha256("<channel_id>:<ts>"). The full
  64-hex digest is the dedup source of truth; the 8-char prefix only
  disambiguates same-day, same-channel filenames.

  YYYY-MM-DD is the message ts in the user's local timezone.

ALTERNATIVE FORMATS:
  --format jsonl   only matches.jsonl (slim ledger, one JSON match per line)
  --format raw     unprocessed Slack response objects under _raw/

PER-MESSAGE JSON SHAPE (the on-disk contract):
  Every field returned by Slack's search endpoint is preserved verbatim,
  with two slackwright additions:
    "channel_id":      <string>          (re-injected so the (cid, ts)
                                          key survives without filename
                                          context)
    "_archive": {                        (single-underscore-prefixed so
       "captured_at":   "<iso8601>",      it can never shadow a future
       "direction":     "in" | "out",     Slack-native field)
       "archive_schema": 2,
       "source_tool":   "slackwright",
       "thread_ts":     "<ts>",
       "search_plan":   "<human summary>"
    }

YAML CACHE SHAPES:
  _users/<id>.yaml:
    id, name, real_name, display_name, email, title, team_id,
    deleted, is_bot, captured_at
  _channels/<id>.yaml:
    id, name, type (channel|im|mpim|group), is_private, is_archived,
    topic, purpose, user (for IMs), members, captured_at

_INDEX.YAML SUMMARY:
  schema_version, tool=slackwright, last_updated, captured_at, format,
  plan (the human summary), query (the rendered Slack search string),
  counts: { created, updated, noop, by_month, by_channel_type,
            users_seen, channels_seen },
  extra: { users_written, channels_written, files: {...},
           search_stats: { pages_fetched, matches_total,
                           matches_unique, chunks, truncated_chunks } }

IDEMPOTENCY:
  Re-running over an existing tree merges cleanly. Per-message file
  outcomes:
    missing on disk             -> created
    present, raw payload same   -> noop
    present, raw payload changed-> updated
  matches.jsonl is truncated at the start of every run (it is a per-run
  ledger, not an append-only log).


--------------------------------------------------------------------------------
5. CLI SURFACE
--------------------------------------------------------------------------------

  slackwright [--state-dir DIR] <subcommand> ...

GLOBAL OPTIONS
  --state-dir   override ~/.cache/slackwright/ (or $SLACKWRIGHT_STATE_DIR)
  --version     print version and exit

SUBCOMMANDS

  login --workspace URL [--timeout SECONDS] [--executable-path PATH]
    Open a headed browser at the workspace, wait for the user to log in,
    then persist the session. Always headed.

  whoami
    Print the saved login bundle (with redacted token).

  doctor
    Probe auth.test against the saved session; print user + team on
    success.

  resolve <value> [--kind {auto,user,channel}] [--headed]
    Show what an arg resolves to (debugging). Auto detects user vs
    channel based on prefix and ID shape.

  fetch [--from PERSON] [--to PERSON] [--with PERSON] [--in CHANNEL]
        [--query "extra terms"]
        [--days N | --since YYYY-MM-DD [--until YYYY-MM-DD]]
        [--max N] [--out DIR] [--with-files]
        [--headless | --headed]
        [--format {archive,jsonl,raw}]
        [--executable-path PATH] [--dry-run] [-v]
    The core extraction subcommand. Defaults: headless, format=archive,
    out=./slackwright-out, no max.

PERSON ARGS (--from / --to / --with) accept any of:
  * U-id (used as-is)
  * email address (resolved via users.lookupByEmail)
  * @handle (matches the `name` field via users.list cache)
  * real / display name (case-insensitive, must be unambiguous)
  * literal `me` / `myself` / `self` (the logged-in user)

CHANNEL ARGS (--in) accept:
  * channel name (with or without leading #)
  * C-id / D-id / G-id (used as-is)

6. SLACK SEARCH QUERY SYNTAX (what slackwright builds)
--------------------------------------------------------------------------------

slackwright maps its CLI flags to Slack's standard search operators:

  --from PERSON   -> from:@<handle>      (or from:<U-id> as fallback)
  --to PERSON     -> to:@<handle>
  --with PERSON   -> with:@<handle>
  --in CHANNEL    -> in:#<slug>          (or in:<C-id> as fallback)
  --since DATE    -> after:<DATE - 1day>  (Slack's after: is exclusive)
  --until DATE    -> before:<DATE + 1day> (Slack's before: is exclusive)
  --query "..."   -> appended verbatim   (any Slack search syntax)

Date inputs accept YYYY-MM-DD, YYYY/MM/DD, or YYYYMMDD.

PAGINATION CAP
  Slack caps any single search at 100 pages * 100 results = 10 000.
  When a date range overflows the cap, slackwright slices it into per-
  month chunks (descending, so the user sees recent matches first) and
  de-duplicates across them on (channel_id, ts). If a single month
  still hits the cap a warning is recorded in _index.yaml's
  search_stats.truncated_chunks; the caller should narrow the query
  with --in / --from / --query and re-run.

7. AUTHENTICATION DETAILS
--------------------------------------------------------------------------------

The login flow:
  1. Open a fresh Chromium context (no storage state) at the workspace
     URL.
  2. Poll page.evaluate(...) every second for window.boot_data.api_token,
     falling back to localStorage.localConfig_v2.teams[*].token if
     boot_data is not exposed (Slack has shuffled this around).
  3. As soon as a plausible xoxc token appears, capture
       workspace_url, api_url, api_token, team_id, enterprise_id,
       user_id, user_name (slack handle), user_real_name, user_email,
       extracted_at
     and persist to <state-dir>/auth.json (chmod 600).
  4. Persist Playwright storage state (cookies + localStorage) to
     <state-dir>/playwright-state.json (chmod 600).

Subsequent fetch calls open a headed-or-headless context with that
storage state and never need to log in again. If the token expires,
the user is asked to re-run `slackwright login`.

HTTP TRANSPORT
  All API calls go through page.request.post() so they share the
  context's cookie jar (including HttpOnly cookies). We add
    Origin: <workspace>
    Referer: <workspace>/
  to mimic what the real web client sends. The xoxc token goes in the
  form body as `token=...`. Retries: 5-step exponential backoff (5s,
  15s, 30s, 60s, 120s) on 429 / 5xx / transport errors. ratelimited
  responses honor the Retry-After header.


--------------------------------------------------------------------------------
8. RESOLVER DETAILS
--------------------------------------------------------------------------------

EntityResolver classifies an input string into:
  * looks like a Slack user/bot id (regex ^[UWB][A-Z0-9]{6,}$) -> use as-is
  * looks like a channel id (regex ^[CDG][A-Z0-9]{6,}$)        -> use as-is
  * looks like an email (regex includes @ and a TLD)           -> users.lookupByEmail
  * literal me/myself/self/i (case-insensitive)                -> bundle.user_id
  * starts with @                                              -> strip and continue
  * everything else                                            -> name lookup

NAME LOOKUP
  Tries the cached @handle index first, then display-name, then real-
  name (case-insensitive exact match). If none match, triggers a one-
  time paginated users.list (cached on disk so subsequent runs are
  instant), then re-tries the indices. Last resort: case-insensitive
  substring match on real_name + display_name. Multiple substring hits
  raise LookupError with the candidate list — never silently picks one.

CHANNEL LOOKUP works the same way against conversations.list.

CACHES
  <state-dir>/users.json          {users: {U_id: profile, ...}}
  <state-dir>/channels.json       {channels: {C_id: meta, ...}}
  <state-dir>/handle-index.json   reverse indices keyed by lowercase
                                   handle / display / real / email /
                                   channel_name + bool flags
                                   (users_listed, channels_listed)


--------------------------------------------------------------------------------
9. FILE DOWNLOAD DETAILS
--------------------------------------------------------------------------------

When --with-files is set:
  * Walk each match's "files" array AND each attachment's nested
    "files" array.
  * Skip entries that look incomplete (mode == "tombstone", missing id,
    missing url_private*).
  * For each unique file id:
      <out>/_files/<F_id>/<safe_filename>
      <out>/_files/<F_id>/_meta.json
  * Idempotent: existing non-empty files are skipped, _meta.json is
    always re-written.
  * Errors per file are recorded in stats but do not abort the run.

10. EDGE CASES AND LIMITATIONS
--------------------------------------------------------------------------------

* Slack search hard cap is 10 000 results / query — chunking by month
  helps but doesn't eliminate. For very high-volume conversations,
  combine --in / --from / --with to narrow the query.
* Edited / deleted messages: search returns the latest content Slack
  is willing to expose. There is no full edit-history API.
* Bot messages: usually have no `user` field, only `bot_id`. The
  resolver short-circuits these with a synthetic record so they don't
  trigger users.info lookups.
* IM channel `name` field is sometimes the other user's id. The
  channel-slug helper detects that and falls back to "im-<short_id>".
* Enterprise Grid: workspace URLs of the form
    https://<workspace>.enterprise.slack.com
  must be passed in full (the short-name shortcut assumes the
  non-Grid form).
* Unofficial endpoint: search.modules.messages is the same endpoint
  the web client uses, so it is stable in practice — but it is not
  part of Slack's public API contract. If Slack changes the response
  shape, slackwright may need an update.


--------------------------------------------------------------------------------
11. TEST STRATEGY
--------------------------------------------------------------------------------

The test suite (under tests/) is pytest-driven and runs in a few hundred
milliseconds. Live Playwright tests are NOT in the default suite — they
need real credentials. Strategy:

  * tests/conftest.py supplies a FakeClient that replaces SlackWebClient.
    It accepts canned responses + dynamic handlers, and records every
    `api(method, params)` call so tests can assert traffic.
  * Pure helpers (query builder, date math, slugifier, hash, payload
    parsers) are unit-tested directly.
  * Resolver, search runner, archive writer, file downloader each have
    their own test file and exercise the full surface against the
    FakeClient.
  * test_integration.py wires resolver + runner + writer together to
    prove an end-to-end fetch produces a complete archive on disk.
  * test_cli.py only exercises the argparse layer — subcommand handlers
    that need live Playwright sessions are not invoked there.

ADDING TESTS
  * Behavior-changing PRs MUST add or update tests. Coverage is not
    enforced by tooling, but the dev.agent's commit checklist (see
    dev.agent.md) requires it.
  * For new Slack response shapes: add a representative fixture to the
    FakeClient registration in conftest.py (or register inline in the
    test) — never depend on live Slack.


--------------------------------------------------------------------------------
12. NON-GOALS / DELIBERATE DECISIONS
--------------------------------------------------------------------------------

* Click vs argparse: argparse is stdlib-only and the CLI surface is
  small enough that argparse is more than enough. Don't pull in click.
* httpx vs page.request: page.request is required so we get the full
  cookie jar including HttpOnly cookies. Don't switch to httpx without
  re-solving the auth-replay problem.
* Async vs sync: sync_playwright keeps the code linear and matches the
  way every other CLI in this space is written. Don't async-ify
  without a measurable benefit.
* `slackdump` integration: deliberately not depended on. slackwright is
  a single-process Python tool with no compiled-binary dependencies.
